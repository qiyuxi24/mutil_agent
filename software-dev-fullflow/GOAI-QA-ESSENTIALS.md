## 二、赛道一硬性门槛（对照自查）

赛道一定位 = **企业级多 Agent 基础设施与协同系统**，核心关键词（Q26）：
1. 多 Agent 协同与编排（任务拆解、上下文传递、状态追踪）
2. 部署与运行基础设施（从 Demo 走向 Production 的工程能力）
3. 安全、审计与可观测（日志、Trace、回滚、审批机制）

**两个硬门槛（Q26）**：
- [ ] 至少 **3 个不同职能 Agent** 的完整闭环设计
- [ ] **Skill 是必选项**（必须设计可复用的 Skill 清单）

**其余硬性要求（Q5）**：
- [ ] 以 **AgentTeams（原名 Hiclaw）** 为协同设计基点（**必须，Q15 明确**）
- [ ] 提交 Agent Identity 清单（附录 A）
- [ ] 闭环覆盖 8 环节：任务输入→拆解→上下文传递→工具调用→结果验证→执行证据沉淀→审批回滚→经验沉淀
- [ ] 从 Agent 记忆存储 / 知识库 RAG / 共享状态管理 / 轨迹可观测 **4 项至少实现 2 项**
- [ ] Skill 为必选；MCP、可观测、RAG 为推荐项

## 三、关键备赛决策澄清（直接影响方案设计）

### 3.1 初赛到底要不要真实部署？（Q12）—— 大幅放宽
- **初赛**：只交方案（完整能力接口设计说明）即可，**不强制真实部署运行**
- **复赛**：建议真实环境运行 + 验证视频/Demo，证明多 Agent 闭环可运行
- **决赛**：现场 Demo（AgentTeams Element 聊天室 或 自研 WebUI）

> ✅ **结论**：初赛以"方案设计文档"为主，无需跑通 AgentTeams。部署/代码包放复赛。**这缓解了当前时间压力。**

### 3.2 要不要用阿里云 Skills？（Q10）—— 不必须
- Skill 是必选项，但**阿里云 Skills 只是推荐工具之一，非强制**
- 可自研 Skills，或使用其他兼容 MCP/Function Call 的 Skill 方案
- 但需在方案中说明**接口兼容性、替换原因与迁移成本**

> ✅ **结论**：我们的 7 个自研工程 Skill 完全符合要求，只需在方案中写清与 MCP/Function Call 的兼容性说明。

### 3.3 是否要求"很底层、能解决所有问题"的基础框架？（Q13）—— 否
- 核心要求是**从实际问题出发**，结合 AgentTeams 及开源组件，构建"可观测、可复用、可审核"的多 Agent 系统，**解决某行业某类实际问题**
- **不要求**做"非常底座化、解决所有问题"的系统

> ✅ **结论**：我们的定位（软件研发缺陷修复 PDCA 闭环）完全契合，不追求底层通用框架。

### 3.4 已有框架/开源 Agent 能否参赛？（Q14/Q16/Q23）—— 可以
- 已有框架可作方案一部分，但**需基于 AgentTeams 构建多 Agent 协同方案**
- 已有作品（未用 AT）集成 AT 后可参赛
- 基于已开源 Agent 改造可以，但**必须用 AgentTeams 作为协调器**，开源 Agent 作为 AT 中的一个 Agent 加入 Team（AT 用的 Qwen/OpenClaw/Harness 本身也是开源 Agent）
- 只要作品最终运行在 AT 上 + 解决某行业通用问题 + 符合赛事标准

### 3.5 能否改造 AgentTeams / 做上层应用？（Q17/Q18/Q21）—— 可以
- 可基于 AT 改造做上层应用；改造部分可作为开源计划贡献回 AT（**建议走贡献回 AT，优于 fork**）
- AT 与其他开源组件的关系：基于 AT + 结合要求列表内/外的其他开源组件，一起解决实际问题即可，重点是"解决实际问题"，**不是重复造协作底座**
- 解决问题 + 沉淀协作组件改进，**完全符合赛道目标**

> ✅ **结论**：我们"基于 AT 的声明式能力造研发 Agent 团队"的路线正确，无需重复造底座。

### 3.6 组件能力不足怎么办？（Q19/Q24）—— 不影响评分
- 发现 AT 或其他组件能力不足：在解决实际问题中提出需求/参与贡献
- 即使暂不支持，只要**方案设计和演示中说明 + 有计划提 issue 和 PR 让 AT 支持**，**不会影响评分**（决赛后提交 PR 也可以）
- 异构 Agent 编排 / 子 Agent 接不同 LLM：AT 支持异构，即便暂不支持也可按上述方式处理

### 3.7 什么样的作品算"AT 协作良好"？（Q20）
- 评判标准以赛题介绍页为准；**能通过 AgentTeams 把 Demo 跑起来，就说明协作良好**

### 3.8 选题方向是否必须企业 B 端？（Q11）
- 不强制，只要方案具备**企业应用价值或可复制到 B 端场景**即可
- 建议方案第一节写清：场景核心难点 / 解决价值 / 多 Agent 闭环如何体现 / 如何迁移扩展到企业

> ✅ 我们软件研发方向天然是 B 端，价值清晰。

## 四、报名 / 组队 / 提交流程规则

- **Q1/Q2**：全球开发者均可报名；支持个人或团队，**团队≤3 人**
- **Q4**：进入决赛原则上需赴杭州线下（9.22-23）；海外团队可线上参加初赛/复赛
- **Q6**：以**个人名义实名注册**；企业背景团队可参赛但报名仍个人实名；获奖补企业主体
- **Q7**：可用商业模型/API，需说明调用方式、依赖边界、开源部分
- **Q8**：鼓励尽量开放，但**不强制完整开放**，推行"有限度、合理化"开放模式，需明确开源协议/第三方依赖/IP 边界
- **Q14**：同一项目可报多个赛道，但需作为独立作品分别评审
- **Q19**：**一个账号只能选一个赛道、建一支队、交一件作品**；可参与两个项目但只能当一队负责人，另一项目以成员加入；双晋级只能选一个继续
