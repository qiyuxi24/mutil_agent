# Skill: diagnosing-bugs（纪律化诊断）

**只对疑难 bug 用；简单 bug 别上重流程。** 核心纪律：**先建反馈环，再谈假设**。除非有明确理由，否则按阶段顺序走，别跳。

排查前先读 `CONTEXT.md`（若有）建立相关模块的心智模型，检查涉及区域的 ADR。

## 先脱敏

凡要展示命令、输出、抓包，**先给每个 secret 打 `<REDACTED>`**；用环境变量构建回环，凭据留在环境而非展示内容里。抓包产物带 auth 头，只引用承载信号的那几行。

## 阶段 1——建反馈环（本 skill 的灵魂）

**有一个「紧」的 pass/fail 信号——在这条 bug 上会变红的那个——你就能找到根因**；二分、假设检验、插桩都只是消费它。没有它，盯再多代码也没用。在这一步**花不成比例的力气，激进、有创造力、拒绝放弃**。

建环手段（大致按此顺序试）：
1. 在触及 bug 的 seam 上写**失败测试**（单测/集成/e2e）。
2. 对运行中的 dev 服务打 **curl/HTTP 脚本**。
3. **CLI 调用** + 固定输入，对比已知正确的 snapshot。
4. **无头浏览器脚本**（Playwright/Puppeteer）驱动 UI、断言 DOM/console/network。
5. **回放抓到的 trace**：把真实请求/payload/事件日志存盘，隔离回放走一遍代码路径。
6. **一次性 harness**：拉起系统最小子集（单服务 + mock 依赖），单函数调用触发 bug 路径。
7. **性质/fuzz 环**：bug 是「有时输出错」，跑 1000 个随机输入找失败模式。
8. **二分 harness**：bug 出现在两个已知状态之间，自动化「启动 X 态 → 检查 → 重复」以便 `git bisect run`。
9. **差分环**：同一输入跑旧版 vs 新版，diff 输出。
10. **HITL bash 脚本**（最后手段）：必须人点，就驱动人按结构化脚本走，捕获输出喂回。

**收紧环**：有了环就把它当产品——能不能更快（缓存/跳过无关 init/收窄测试范围）？信号能不能更锐（断言具体症状而非「没崩」）？能不能更确定（钉死时间/固定 RNG/隔离文件系统/冻结网络）？30 秒的 flaky 环≈没环，2 秒的确定环是调试超能力。

**非确定 bug**：目标不是干净复现，而是**更高复现率**。循环触发 100 次、并行、加压、收窄时间窗、注入 sleep。50% flaky 可调，1% 不可调——不断抬到可调为止。

**实在建不出环**：停下明说，列出试过什么，向上游要：(a) 能复现的环境权限，(b) 脱敏抓包（HAR/日志 dump/core dump/带时间戳录屏），或 (c) 临时加生产插桩的许可。**没有环就跳去假设 = 本 skill 要防止的失败模式。**

**阶段 1 完成标准**：环「紧」且「能红」——你能说出**一条命令**（脚本路径/测试调用/curl），已跑过至少一次（展示调用 + 脱敏输出），且：能驱动真实 bug 路径并断言**用户的确切症状**（能在此 bug 上红、修好后绿）；确定；快（秒级）；Agent 可无人值守运行。

## 阶段 2——复现 + 最小化

跑环，看它变红。确认：环产生的是**用户描述的**失败模式（不是碰巧的相邻失败）；跨多次可复现；已捕获确切症状。**变红后**，把复现缩到「仍会红」的最小场景——输入/调用方/配置/数据/步骤**一次只切一个**，每切一次重跑环。目的：最小复现缩小子阶段 3 的假设空间，并成为阶段 5 的干净回归测试。

## 阶段 3——假设

测试任何假设**之前**先列 **3-5 个排序假设**（只生成一个会锚定第一个看似合理的想法）。每个假设必须**可证伪**，说出它的预测：`如果 X 是根因，那么改 Y 会消除 bug / 改 Z 会加重`。说不出预测 = 这是感觉，丢弃或锐化。**把排序清单给上游看**——他们常有领域知识能瞬间重排。别干等，没回应就按你的排序推进。

## 阶段 4——插桩

每个探针映射到阶段 3 的一个具体预测，**一次只改一个变量**。工具偏好：能断点就别打日志（一个断点胜过十条日志）→ 在区分假设的边界打**定向日志** → 绝不「全打日志再 grep」。**给每条调试日志加唯一前缀**（如 `[DEBUG-a4f2]`），清理时一条 grep 全清。**性能分支**：性能回退通常日志没用，先建基线测量（计时 harness/profiler/查询计划）再二分——**先量后修**。

## 阶段 5——修复 + 回归测试

**在修复之前**写回归测试——但只在有「正确的 seam」时。正确 seam = 测试覆盖 bug 在调用点**真实发生的模式**。seam 太浅（单调用方测不了多调用方链）会给假信心。**没有正确 seam 本身就是发现**：标注它——代码架构在阻止 bug 被锁定，交给下一阶段。有正确 seam 时：最小复现转失败测试 → 看它失败 → 应用修复 → 看它通过 → 用原始（未最小化）场景重跑阶段 1 环。

## 阶段 6——清理 + 复盘

宣布完成前必须：原始复现不再复现（重跑阶段 1 环）；回归测试通过（或 seam 缺失已记录）；所有 `[DEBUG-…]` 插桩已清（grep 前缀）；一次性原型已删；**命中的假设写进 commit/PR 说明**（让下一个调试者学到）。**然后问：什么能预防这个 bug？** 若答案涉及架构变更（没有好测试 seam、调用方纠缠、隐藏耦合），把细节交给 `codebase-design` / 架构改进思路——在修复落地**之后**提，因为你此刻比开始时信息更多。

## 输出

- 诊断报告（反馈环命令 + 命中假设 + 修复 + 回归测试），落 `shared/tasks/{id}/` 并复用 `evidence-log`。

## 安全边界

- 所有展示内容脱敏；插桩只加临时前缀日志、事后必清；修复走独立分支。
