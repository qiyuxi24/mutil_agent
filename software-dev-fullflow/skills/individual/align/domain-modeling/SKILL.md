# Skill: domain-modeling（领域语言建模）

**让 Agent 用「1 个词」说清楚「20 个词」才能说清的事。** 项目里术语越乱，Agent 越啰嗦、越容易跑偏。本 skill 主动打磨一份共享词汇表 `CONTEXT.md`，作为团队统一语言。

## 执行步骤

1. **查现有词汇表**：先读项目根/任务域的 `CONTEXT.md`（若不存在则本轮第一个术语敲定时创建）。
2. **挑战冲突术语**：发现上游/产出里用了与词汇表冲突的词，立刻指出——「词汇表定义 X 是 A，你现在似乎指 B，是哪一个？」。
3. **收敛模糊语言**：遇到含糊/过载的词，提出精确的规范词——「你说的『账户』指 Customer 还是 User？这俩是不同概念」。
4. **用具体场景压测**：发明边界场景，逼出概念间的精确边界（如「部分取消」到底成不成立）。
5. **与代码对账**：拿代码行为核对话语——「代码是整单取消，但你刚说支持部分取消，以哪个为准？」。
6. **即时回写**：术语一敲定就立刻写进 `CONTEXT.md`，不攒批。格式：`术语 = 定义`，只写术语，**不写实现细节**（它不是 spec、不是草稿本）。

## 输出

- `CONTEXT.md`（根级单语境，或多语境时 `CONTEXT-MAP.md` 指向各处）。
- 术语敲定记录，供后续 Agent 引用，避免重复解释。

## Gotchas

- **CONTEXT.md 是「词典」不是「说明书」**：只放术语定义，不放实现方案、不放 TODO。
- **ADR 克制**：只有「难逆转 + 无上下文会困惑 + 真实权衡」三者同时满足才写决策记录（ADR），否则跳过。
- **越用越省**：术语统一后，变量/函数/文件命名跟着统一，Agent 导航代码更快、思考更省 token。

## 失败处理

- 术语冲突无法仲裁 → 记录两个候选 + 各自影响，@mention 领域 owner 定夺。
- 代码与话语矛盾 → 以代码为准修正话语，并标注「代码已偏离原意图，建议另开任务」。

## 安全边界

- 只写词汇表文档，不改业务代码、不改生产配置。
