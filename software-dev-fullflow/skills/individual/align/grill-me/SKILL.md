# Skill: grill-me（开工前拷问）

**最省时间的一步是动手前把事问清楚。** 接到任务先别急着干，先进入「拷问」模式——把模糊的需求拆成一棵设计树，逐分支追问，直到每个分支都有明确答案。这是个体 Agent 消除对齐偏差的第一道纪律。

## 执行步骤

1. **读任务规格**：先读 `shared/tasks/{id}/spec.md`（若无则向 Manager/Aggregator 索取），提取本次要交付的**目标**与**验收标准**。
2. **拆设计树**：把需求拆成可追问的分支——目标、边界（做什么/不做什么）、输入输出、约束、验收口径、风险。每个分支是一个待解节点。
3. **逐分支拷问**：对每个模糊分支发起追问，一次只问一个最关键的，不要一屏抛一堆问题。追问要具体、可回答，逼出可执行的答案，而非「大概/差不多」。
4. **识别「不知道要问什么」的地方**：主动指出规格里**没写但很关键**的盲区（如：失败时怎么办？边界值？并发场景？回滚预案？），列出候选问题供上游确认。
5. **收敛为可执行契约**：所有分支有了答案后，把结论**回写**成 `shared/tasks/{id}/spec.md` 的补充（或 `clarifications.md`），作为后续执行的输入契约。

## 输出

- 更新后的 `spec.md` / `clarifications.md`：每个已解分支一句话结论 + 仍未解决分支清单（标注阻塞/不阻塞）。
- 若关键分支无解且阻塞执行 → 通过 @mention 上游（Manager/发起者）追问，**不带着未解疑问硬干**。

## Gotchas

- **别把「沉默」当「同意」**：上游没回 ≠ 可以按自己猜的做。关键分支无解先等确认，或显式声明「按假设 A 执行，若不对请纠正」。
- **一次只追一个分支**：一次抛 10 个问题 = 一个都不答。追到最关键的，答完再下一个。
- **拷问是手段不是目的**：一旦契约清晰就停，不要为问而问，拖慢闭环。

## 失败处理

- 上游长时间无响应 → 用「假设声明」继续（明确写下假设），同时在产物中标注待确认项。
- 需求本身自相矛盾 → 记录矛盾点，@mention 发起者仲裁，不自行二选一。

## 安全边界

- 只读 + 可写任务规格文件，不改代码、不改生产数据。
- 涉及敏感信息的追问与结论需脱敏后落盘。
