# 企业绩效管理体系对标参考（KPI Benchmark）

> GOAI 大赛 · 赛道三「软件研发全流程协同」· 成员评价体系的**权威对标 + 增量增强**
> 解决的问题：我们的成员评价体系（`AGENT-EVALUATION.md` 三层模型）已自洽，但缺"真实大厂管理实践"背书。本文档回答：**这套 KPI 不是拍脑袋，而是对标华为 PBC、IBM Check-in、Google OKR+GRAD、平衡计分卡 BSC 等经过验证的企业绩效管理体系**，并给出可落地增量。
> 对应评审权重：**场景价值 25%**（把 LLM Agent 当"数字员工"治理）+ **工程落地 20%**（可量化、可审计）。
> 日期：2026-08-13

---

## 0. 结论先行

> 我们把 LLM Agent 当作"**数字员工**"来治理，因此直接对标真实大厂"员工绩效管理"的方法论是**同构且权威**的。现有三层模型并非自造概念，而是大厂实践在"AI 公司"场景下的映射。

| 标杆体系 | 一句话本质 | 我们已有对应 | 本文新增增量 |
|---------|-----------|-------------|-------------|
| **华为 PBC** | 结果导向 + Win/Execute/**Team** 三维 + IDP + 末位淘汰 | 合格度（结果）/ 治理（裁员） | 补「团队协作」「个人成长」两维 |
| **IBM Check-in** | PBC 敏捷化：季度复盘 + 五维持续评估 | 合格度（持续 KPI） | 补「持续 Check-in」而非一年一评 |
| **Google OKR+GRAD** | OKR 管目标（不打分）+ GRAD 管人才（影响力） | 贡献度（影响力）/ 治理 | 明确「目标管理 ≠ 考核打分」分离 |
| **BSC 平衡计分卡** | 财务/客户/内部流程/学习成长 四维 | 合格度（内部流程） | 补「学习成长」参与评分 |
| **SMART/360/强制分布** | 目标设定与评估的通用工具 | 里程碑（目标）/ 下游采纳（peer） | 补结构化 360 + 评级校准 |

> **核心判断**：现有合格度 ≈ BSC 的"内部流程"、贡献度 ≈ Google 的"影响力"、治理 ≈ 华为的"结果应用"。**骨架是对的**，本文不推翻，只补盲区 + 提供权威论据。

## 1. 为什么"AI 公司"能抄"大厂 HR"（方法论同构）

6 个 LLM Agent 组成"AI 公司"动态团队（`agents/AGENT-IDENTITY.md`），给 Agent 团队做绩效与给人类公司做绩效面临**完全相同的问题**：

| 问题 | 人类公司 | 我们的 AI 公司 |
|------|---------|---------------|
| 怎么衡量"做得好不好" | KPI/OKR | 合格度（确定性闸门） |
| 怎么衡量"贡献了多少" | 绩效排名/影响力 | 贡献度（采纳分/反事实） |
| 怎么决定"留任还是淘汰" | 结果应用 | 治理（retain/coach/fire） |
| 怎么避免"只看产出不看人" | 360 度/价值观 | 待补（本文 §3.5） |

大厂花了数十年踩坑验证过的方法论，就是我们最权威、最省成本的参考。

## 2. 四家标杆企业绩效体系调研（经核实）

### 2.1 华为 PBC（个人业务承诺）

- **起源**：源自 IBM 战略绩效管理系统，华为引入并本土化，成为其战略落地核心支柱（华为本身也是"抄 IBM"，证明标杆可迁移复用）。
- **三维**：① 业务目标（KPI 结果量化）② 人员管理目标（管理者）③ **个人发展目标（IDP）**。
- **Win/Execute/Team**：继承 IBM 经典三问——赢取业务、高效执行、**团队贡献**。
- **结果应用**：结果导向 + **末位淘汰**（每年约 5% 的 C/D 档强制分布）。
- **内核金句**："以奋斗者为本，以结果为导向" → 我们：**以产出物（artifact）为本，以确定性闸门为导向**，不靠 Agent 自评。

### 2.2 IBM PBC → Check-in / Checkpoints

- **PBC 首创者**，是华为等体系的源头，权威性拉满。
- **2016 变革为 Check-in**：考核周期从年度改季度，目标更敏捷；用 **Checkpoints 五维**持续评估，取代一年一次大考核。
- **变革初衷**：减少文书负担、更关注员工发展 → 与我们"轻量方案零重跑"同一价值观。

### 2.3 Google OKR + GRAD

- **OKR**（Objectives & Key Results，源自 Intel 的 Andy Grove，John Doerr 引入 Google）：**目标对齐工具，明确不与薪酬晋升挂钩**，避免"目标博弈"。
- **GRAD**（Googler Reviews and Development，2022）：替代一年两次 Perf 考核，**一年一次**，从**影响力（impact）**角度评估人才。
- **减负动机**：仅 47%-53% 员工认为旧考核"值得花时间" → 我们的"轻量优先、精确可选"正是减负导向。
- **关键判断**：Google 是"**OKR 管目标 + GRAD 管人才**"双轨 → 目标设定与人才评估应分属两个机制。

### 2.4 BSC 平衡计分卡（Kaplan & Norton，1992）

| 维度 | 含义 | 我们的对应 | 现状 |
|------|------|-----------|------|
| 财务 | 经营结果 | 项目成功交付 | 闭环跑通 |
| 客户 | 客户满意 | `_verify` 闸门 | ✅ |
| **内部流程** | 流程质量 | **合格度** | ✅ 已覆盖 |
| **学习与成长** | 组织能力沉淀 | Retrospector + RAG | ⚠️ 有机制**但未纳入评分** |

> BSC 的"四维平衡"提醒：不能只评"质量"一个维度，"学习成长"有机制却**没作为 KPI 参与评分**，是明显盲区。

### 2.5 通用配套工具

| 工具 | 本质 | 现状 |
|------|------|------|
| SMART 原则 | 目标要 Specific/Measurable/Achievable/Relevant/Time-bound | 里程碑已满足 S/M/T，需强化 A/R |
| 360 度评估 | 多来源反馈（上级/同事/下属/客户） | 下游采纳是 peer 的轻量版 |
| 强制分布 | 评级正态校准（GE 20-70-10） | 三级评级**无校准**，易全员高分 |
| 能力素质模型 | 岗位胜任力拆解 | 分角色 KPI 已是雏形 |

## 3. 增量增强建议（"添砖加瓦" 6 条核心落点）

### 3.1 借鉴华为 PBC → 合格度补「团队协作 + 个人成长」两维

**盲区**：现有 `QUAL_WEIGHTS` 全是"个体产出质量"，缺华为最看重的"Team"和"IDP"维度。

**落地**（供 `evaluation.py` 参考，从原五项拆出协作）：
```
新 QUAL_WEIGHTS = {
  once_pass:    0.25,   # 一次通过率（原 0.30）
  completeness: 0.20,   # 产出完整性（原 0.25）
  protocol:     0.15,   # 协议合规（原 0.20）
  teamwork:     0.15,   # 【新增】团队协作：@mention 正确交接、零噪音
  timeliness:   0.10,   # 时效（原 0.15）
  auditability: 0.10,   # 产出可审计（原 0.10）
  growth:       0.05,   # 【新增】个人成长：打回反馈后一次通过率是否提升
}
```

### 3.2 借鉴 IBM Check-in + Google OKR → 「持续 Check-in」+「目标/评估分离」

- **持续 Check-in（IBM）**：不只在一轮任务结束时算一次分，每个里程碑推进时**增量追加** `scorecard.json`（现有 `save_scorecards` 改为追加历史趋势，而非覆盖）。
- **目标/评估分离（Google OKR）**：里程碑握手词只表示"目标达成"，**不直接等于高分**；高分取决于达成后的**影响力（下游采纳）**，防止 Agent 为刷里程碑而刷。

### 3.3 借鉴 Google GRAD → 贡献度升级为「影响力」三档

把现有"采纳分"（token 重叠的浅近似）升级为三档影响力：
- **L1 直接采纳**：下游产出直接引用上游结论（现有 token 重叠）。
- **L2 关键依赖**：下游不采信上游就无法推进（`MILESTONE_WEIGHT` 已部分体现）。
- **L3 复用外溢**：该产出被**跨任务** RAG 检索复用 → 影响力最高形态，现有模型**未计**。

### 3.4 借鉴 BSC → 治理层引入「学习成长」权重

现有治理只看综合分，低估了 Retrospector 的"长期复用"价值。改为：
```
治理综合分 = 0.5 × 合格分 + 0.35 × 贡献分 + 0.15 × 成长分
成长分 = Retrospector 沉淀知识被后续任务 RAG 命中的次数（跨任务累积）
```

### 3.5 借鉴 360 度 → 三向 peer 反馈结构化

| 反馈来源 | 现实 360 对应 | 确定性信号 |
|---------|--------------|-----------|
| 下游 → 上游 | 同事评价 | 下游 token 采纳度（已有） |
| 上游 → 下游 | 上级评价 | 打回次数 reject_count（已有） |
| 用户/客户 → 全员 | 客户评价 | 最终 `RELEASE_OK`、线上缺陷复现率（**新增**） |

### 3.6 借鉴强制分布 → 评级校准（防"全员高分"）

绝对阈值（≥85/60-84/<60）之外叠加"相对锚定"（**不照搬 20-70-10 僵硬比例**）：
- 某次任务全员 ≥85 且方差极小 → 提示"评级失灵"，触发精确反事实法；
- 某 Agent 连续 N 次任务排名末位 → 即使绝对分 ≥85 也标记"需观察"（对齐华为末位淘汰的"连续"条件）。

## 4. 分角色 KPI 增量总表

| 角色 | 现有 KPI（已定义） | 本文新增 KPI（大厂对标） |
|------|------------------|------------------------|
| Aggregator 聚合 | 去重率、spec 字段完整 | spec 下游采纳率（GRAD）；需求遗漏率（BSC 客户） |
| RootCause 定位 | 根因确定性标注、影响面覆盖 | 根因被采纳后修复成功率（GRAD L2）；根因误判返工次数（360） |
| Fixer 修复 | 编译/静态分析通过、一次通过率 | PR 验证通过率（360 客户）；跨任务代码复用率（BSC 成长） |
| Tester 测试 | 测试金字塔、覆盖率、报告完整 | 漏测率（闸门失守）；打回决策被采纳率（GRAD） |
| Releaser 发布 | 金丝雀健康、审批留痕、回滚记录 | 线上缺陷复现率（BSC 客户）；发布稳定性（华为结果） |
| Retrospector 复盘 | 知识四要素结构化 | 知识跨任务 RAG 复用率（BSC 成长，**权重最高**） |

## 5. 评审亮点（供 PPT/简介引用）

- **方法论有出处、可对标**：评价体系不是自造，而是华为 PBC（结果导向+Team+IDP+末位淘汰）、IBM Check-in（持续评估）、Google OKR+GRAD（目标/评估分离+影响力）、BSC 平衡计分卡（四维平衡）在"AI 公司"场景下的落地。
- **把 Agent 当"数字员工"**：将成熟的"企业 HR 绩效管理"迁移到 LLM 团队，场景价值从"自动化流水线"跃升为"**AI 公司治理**"。
- **补齐盲区**：新增团队协作、个人成长、学习成长（组织记忆复用）三个大厂标配维度，解决"只看产出不看人"。
- **工程可落地**：所有增量均可落到 `evaluation.py` 的确定性信号，零额外 LLM 成本，延续"客观优先、可审计"原则。
